# Selector2 callback binding - 2026-10-27

The selector2 source path is reached through a stored callback descriptor and a short receiver-adjustment thunk. The thunk leaves the incoming RDX argument unchanged. This extends [the source-pointer trace](NATIVE_SELECTOR2_SOURCE_2026-10-27.md); it does not identify the creator or historical contents of the incoming object's `+0x18` pointee.

All addresses below are hexadecimal RVAs. The [observation](../observations/selector2-callback-binding-2026-10-27.json) records the byte-source and decoder witnesses. The source is the existing analyst-derived static 98348 text patch, not an unaltered PE section or runtime capture.

In the covered `CDB030` record, `CDB992` loads the address of `CD6D30`. A conditional initialization path stores that address at global `3771348`; the signed DWORD adjustment at `3771350` comes from R15D, zeroed in the prologue. The path tests and sets bit0 of global `3771358`. The full sixteen-byte store includes padding for which no independent zero-value claim is made. If initialization is skipped, or another writer changes these globals, the stored function and adjustment are not established by this path.

The following block uses `QWORD[3B7C6B0]+0x4A0` as a helper receiver and the nonnull registration receiver's `+0x10` address as its second argument. It calls opaque helpers `2DE170` and, conditionally, `2DE340`; the latter's returned slot receives the address of `CD1660` at `+0x10`. Lookup, insertion, ownership and event-type semantics of those helpers remain unresolved. Calling this a registration is an inference from the repeated organization and stored callback addresses.

The explicit `CD1660..CD167F` thunk is 31 bytes and seven instructions. It reads a signed DWORD adjustment from `3771350`, computes `entry_RCX + adjustment - 0x10` for nonzero entry_RCX, and uses the adjustment itself when entry_RCX is zero. It then tail-jumps through `QWORD[3771348]`. It writes no RDX register or source memory. With a stable initialized descriptor, zero adjustment, a nonnull entry receiver equal to `owner+0x10`, valid arithmetic and normal ABI behavior, this forwards the owner and the unchanged incoming argument to `CD6D30`. It neither creates that argument nor writes its `+0x18` field.

A narrow scan of selected global-load and nearby `+0x4A0` address forms also found a block at `CDE2EC`. Its selected fragment repeatedly passes the same receiver-derived key through many fields to `2DE690`; it provides no authenticated producer of the incoming payload. The scan does not cover every accessor, alias or indirect flow. A separate exact leaf-getter-pattern scan found one unqualified candidate and no direct E8 callers; that result supplies no missing event identity.

GNU objdump 2.42 in the already-running Ubuntu instance decoded the 4,186-byte `CDB030` record through RET and the 31-byte thunk. All 974 emitted instruction rows were checked against guarded source bytes. This is bounded static evidence, not whole-program control-flow or runtime evidence. A prior IDA prefix attempt failed with exit20; its stop address was not recorded. The selected window cut through the seven-byte instruction at `CDB9CE`, but this does not establish the original failure's exact location. The later IDA diagnostic attempt stopped at the disk-capacity guard before launch. These attempts remain preserved and are not counted as successful analyses.
