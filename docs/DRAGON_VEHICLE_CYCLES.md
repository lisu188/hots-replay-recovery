# Dragon Knight generations and pilot ownership

Five TEN_GREYMANE pings refer to the Dragon Knight. One references the second generation. The other four reference the fourth generation, including one before anyone piloted it. Each activation records a capture counter and team. A unique same-loop transfer to a player on that team independently identifies the vehicle. The initial statue and every later neutral spawn occupy the map-authored position. After death, the installed timer waits 90 game seconds before a 30-second warning. The next neutral statue appears 1,920 loops after death.

Across four build-41810 matches and fifteen build-98348 matches, all 51 subsequent spawns agreed with the timer and all 65 activations agreed with the owner-transfer lookup. In the historical recordings, both control and upkeep pass to the pilot. In the 52 current-build activations, control passes to the pilot and upkeep belongs to the team's computer player. The converter reproduced the 52 physical target tracker frames across 1,096 bytes. [Per-recording results](../observations/dragon-vehicle-cycles.json)

For TEN the standalone target-format projection contains four activation transfers (88 bytes) using the original recorded vehicle generations. Whether those numeric generations would recur on the reconstructed historical map is unresolved. The five pings can be rebound by objective generation when an independently generated destination trace exists. The matcher checks the birth, destruction, activation, pilot and team, and rejects ambiguous matches and out-of-lifetime references. The output is kept separate from the historical tracker to preserve its recorded ownership.

Run `python dragon_vehicle_cycles.py --mechanics MapMechanicsLib.galaxy --header MapMechanicsLib_h.galaxy --case REPLAY SHA256 BUILD MAP`. Repeat `--case` for additional samples. For one 41810 sample, `--retained-owner-output NEW.bin` saves the sparse projection. The tool checks whole-file hashes for the map, replay and both installed Galaxy members.
