# Empty permission-list conversion review — 2026-10-19

The evidence supports implementing an explicit, data-specific **empty-list framing conversion** for the five original MapInfo records and an isolated175-bit ClientInfo segment. It does not support a complete ClientInfo conversion that changes only that segment. Missing historical native field names alone need not block an observed encoding profile; the profile must state its model and refuse inputs outside the observed branch.

The saved evidence covers30 ClientInfo record observations: original10, the same ordered source data in R8's10, and10 from the separately authenticated39445 control. This is20 record observations from independently acquired replays, not30 independent samples and not a count of unique people/accounts. The39445 schema1 diagnostic remains a separate control; its missing party optional is not silently merged into the original schema2 profile.

All five original package headers have full digest and lossless versioned-wire bindings. All75 explicitly shared header/MapInfo fields match. In particular, root/0/17 is an actual ARRAY tag with zero elements in every header, including the original map. This supplies independent source-package evidence for the empty value at the corresponding MapInfo field; it was not synthesized from a missing tag. The complete current header schema still fails all five old headers because of retained old tags6,11,23 and missing current24. The partial common-field correspondence does not authenticate a whole old native schema or all historical permission semantics.

Current native MapInfo.requiredPermissions and ClientInfo.relevantPermissions both reference type1828, Permission::HandleList:31-bit count, zero minimum, with96-bit handles. Current ClientInfo's fields immediately before the count occupy168 bits (8+64+96). Every saved old record has the independently anchored175-bit candidate span, candidate7count zero, exact first-five-field prefix endpoint, matching following anchors, and an impossible unchanged31-bit interpretation. Under the explicit model of an unchanged168-bit prefix followed by one count plus96-bit elements, the equation175=168+w+96n has only(w=7,n=0) for count widths0..31 and nonnegative element count. The saved-evidence helper checks every width algebraically. This is conditional uniqueness within that model; it does not rule out an unmodeled historical field or padding.

A narrow implementation should enforce the following requirements:

1. Admit the exact original/R8 source identities and already validated legacy profile first. Bind member SHA, all five module identities/prefix hashes/terminal digests, source-record start/end boundaries, unchanged historical full-member reconstruction and private details/initData identity/seed checks. Keep39445 a separate diagnostic profile unless separately admitted.
2. Parse the proposed legacy list at the exact named/profile-bound position, require its seven-bit count to be zero, and reject nonempty counts immediately. For original MapInfo, also require the five explicit header ARRAY17empty controls and all75 common positive comparisons. Never infer an empty list from a missing header tag or parse failure.
3. Preserve the original non-count tokens and bit spans. Encode the logical empty list with the authenticated current type1828 count framing (31zero bits), replacing the seven-bit zero count and adding24bits at that position. Do not overwrite the following24 source bits or append arbitrary zeros to a whole opaque block. No permission element, donor value or account data is introduced.
4. Independently decode the target MapInfo record with the unchanged current32-field reader and require exact destination boundaries and an empty list. For the isolated ClientInfo segment, use the current reader through the ninth field, preserving all168 source bits and checking the following rating/flags/build anchors at their shifted positions. Do not claim full current ClientInfo success from this partial check.
5. Invert the declared framing edits and require exact recovery of the original source spans/member. Check every unaffected field/span for exact preservation. Reject wrong boundaries, mutated nonzero counts, wrong module identity/digest, missing arrays, leftover bits and target-end mismatches. These checks can falsify an incorrect decomposition without requiring unavailable historical native names.
6. Before admitting complete ClientInfo, account explicitly for every additional current field and use the independent full current ClientInfo/OnlineStartGameRequest reader to check ends and EOF. Count widening does not provide their values. A declared migration policy for genuinely new fields is a separate operation from a source-proven value transfer; no such policy is authorized or applied by this design report.

The last requirement is material. Current ClientInfo additionally has mandatory m_playerLevel32 and m_hasActiveBoost1 after the nickname. The current Hero shared-player structure also contains m_isLobbyVoiceSilenced, m_isTeamVoiceSilenced and m_isBlizzardStaff; the historical source profile has only silence before party, while the current-tail source explicitly adds those three flags. These are36 additional current-only bits for the observed Hero layout, beyond permission count widening. This report does not fill them. The old summaries' choice2 histogram describes TalkerId, not the shared-player S2/Hero branch; it supplies no branch histogram for those later fields.

The source schema offers a candidate32-bit field but no proved alias. Official41810 initData declares optional m_combinedRaceLevels; the same named optional remains in96477. In the full current native graph, that name is under SharedPlayerInfo::InfoS2, separate from ClientInfo.m_playerLevel. Exact pinned HTC source skips combinedRaceLevels rather than assigning it to player level. That prevents treating the name or a numeric coincidence as an established account-level conversion. A useful next check would bind a primary producer/consumer mapping, or independently falsify the alias against correctly joined current native/core fields. Hero gameplay level events must remain distinct.

For boost, official41810 has no named m_hasActiveBoost field. Official96477 lobby slots do. The immutable HTC parser reads voice-silence status at builds>=61718, staff status>=66977, and active boost>=69947. These version gates document that parser's supported field presence; they do not prove that older users lacked Stimpack/boost entitlements. The old m_licenses array has no demonstrated license-to-active-boost mapping here. The official tracker schema's generic stat-event key/value container can carry dynamic names, so schema-text absence cannot establish absence from all historical tracker events. No raw tracker was reread.
